> *This was generated by AI from a spike run with the maintainer, who made each decision below.*

## Recommendation

**Use the lock for task runs, with "unknown" as the answer wherever it can't be trusted. Don't use it for service instances: the daemon already serialises a concurrent `up`.**

The lock was right in every case container state gets wrong. It has one way of being wrong itself, found here, and that way can be made to read unknown.

## What was run

A throwaway patch to `ratect-core/src/engine.rs` made each task run take an exclusive `flock` on `<runs dir>/<run id>.lock` as soon as its run ID exists, and hold it until the run's function returns. A script then listed every container carrying a run label and tried each run's lock: taken reads **dead**, refused reads **alive**, no file reads **unknown**. Everything ran against OrbStack (Docker 29.8.2, Linux VM) on macOS. The code is on a local `prototype/875-run-lock` branch, under `prototype-875/`; it has not been pushed.

## Answers

### 1. Does it prove death where container state is wrong?

Yes, in all three cases.

| Case | Container state | Lock, process alive | Lock after `SIGKILL` |
| --- | --- | --- | --- |
| Control: killed mid-task | dependency running, task running | alive | dead |
| Killed during cleanup | dependency running, no task container | alive | dead |
| Task exited, output draining into a stalled pipe | task exited | alive | not applicable: the run then ended normally |
| Killed while a dependency's setup command ran | dependency running, task created | alive | dead |

### 2. One invocation, several task runs

One lock per task run. A prerequisite's run cleaned up and released its lock before the main task's run began, including under `--no-cleanup-after-success`, which spares only the main task. Two runs of one invocation never had containers at the same time.

`resources` needs no mapping: the lock file is named for the run label's value.

Four concurrent runs of one task in one project each read alive under their own file, and killing one turned only that one dead. Run IDs are fresh UUIDs, so no two runs open the same file.

A per-invocation lock would need a second label on every container, and would keep a finished prerequisite's leftovers reading alive for the rest of the invocation.

### 3. Where the lock can't be seen

**A visible lock file is not a visible lock.** With the directory bind-mounted into a container, the container took a lock the macOS host was holding, and the host took one a container was holding. A second host process was correctly refused. So Ratect in a container that shares the host's `~/.ratect` would read every live host run as dead.

The guard: the holder writes its kernel's boot identity into the file (Linux `boot_id`, macOS `kern.bootsessionuuid`), and a free lock is trusted only by a process with the same one. Two separate containers reported the same `boot_id` and the Mac a different identity, so this separates "same kernel" from "same file" where the probe needed it to. A cost: after a reboot, every earlier run reads unknown though it is certainly dead. A machine identity would tell those apart, but the one image checked (Alpine) has no `/etc/machine-id`, and unknown is the safe answer.

**An absent file can't say why it is absent.** Seven running task containers from other projects were on the same daemon, made by binaries without the patch. All read unknown. A deleted file would look the same, which is what point 4's rule is for.

A remote daemon, a second machine and another user's home were not run. Each gives an absent file or a different boot identity, so each reads unknown by the rules above.

### 4. Lock file lifetime

- The holder creates the file under a temporary name, locks it, writes a format line and its boot identity, and renames it into place, all before it creates anything on the daemon. A file visible under its final name is then always locked, or its holder is gone.
- A run that cleaned up fully deletes its file. A run that leaves anything behind leaves the file too.
- `resources clean` deletes a dead run's file after removing the run's resources. It may also delete a file whose run no longer appears on the daemon, when it can prove that holder dead.
- So an absent file means another machine or user, an older binary, or a file deleted by hand, and reads unknown.

0023's removal race can't occur: no starting run ever opens an existing file. The prototype removed no files, so none of this was run.

### 5. Windows

Not probed; nothing here runs Windows code. `File::try_lock` exists there and Windows releases a lock when its holder dies, but neither can be tested. Non-Unix takes no lock and reads every run unknown. A follow-up issue in the Windows milestone, blocked by #265, will track doing better (compare #868).

### 6. Service instances

The daemon serialises a concurrent `up`, and a file lock isn't needed. Five pairs of concurrent `docker create` with one name each produced exactly one winner; the loser got `Conflict. The container name ... is already in use`. A concurrent pair of `docker network create` behaved the same way. This works across machines and inside containers, where the file lock does not.

What follows from using it:

- An instance's container and network names are deterministic: project, service group, instance, container. The instance is in the name from 0.14.0, so #873 changes no scheme.
- The guard is per resource. The `up` that loses a create adopts that container, and two `up` may each win different members of one instance.
- A name held by something without the instance's labels is refused with an error. It is never adopted or removed. Labels remain the identity.
- No lock for a foreground `up` in 0.14.0. A killed foreground `up` leaves an instance that behaves exactly as a detached one, so knowing whether anything is attached would change a display column and no behaviour.
- An instance whose members have all exited is selected by `resources` by default. No process owns it, so there is no death to prove and no unknown state.

### 7. What `resources` does with "unknown"

| State | How it is reached | Selected |
| --- | --- | --- |
| Dead | lock free, same boot identity | by default |
| Alive | lock refused | never; end the process first, and the run then reads dead |
| Unknown | no file, another boot identity, no recognised format line, an error from the lock, non-Unix | only with `--all`, where `--older-than` is the guard |

On upgrade, every leftover from an older binary is unknown and needs `--all`, even with all its containers stopped. That was chosen over selecting stopped-but-unknown runs by default: such a run may be another machine's live run draining output.

A run that can't take its lock (no home directory, a read-only one, a filesystem that refuses the lock) still runs, with a debug log line only. Its leftovers read unknown.

## Not varied

- A native Linux daemon, where a container and the host share a kernel and the lock should be visible through a bind mount.
- Docker Desktop, a remote daemon, a second machine, another user's home, a home directory on a network filesystem.
- Windows.
- File removal and the temporary-name rename: designed here, not built.
- The lock's `ratect` side: only `ratect-compat` was run. Both share the engine.

## What this changes elsewhere

- **#265** can be briefed against points 2 to 4 and 7.
- **`decisions/0025`** (draft): Decisions 2 and 3 change from container state to the lock and the three states; Decisions 5 to 7 stand, with deterministic names added to 6 and 7 reworded for all-exited instances.
- **`decisions/0023`**: Decision 3 says the kernel releases a holder's lock for every process "whatever PID namespace or bind mount it sees the file through". The bind-mount half is false across a VM boundary. There the effect is two cloners at once, which 0023's staging already makes safe. A separate issue will correct the wording and decide whether the entry lock wants a boot identity too.
